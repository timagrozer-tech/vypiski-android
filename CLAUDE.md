# Инструкции для Claude — REVVL Camera Lab

Перед работой прочти документы уровнем выше (`02_МАСТЕР_ПРОМПТ_ДЛЯ_CLAUDE.txt`, ТЗ, дорожная карта), `README.md` и `TEST_PLAN.md`.

**Устройство:** REVVL 7 Pro 5G; Snapdragon 6 Gen 1; 8 ГБ RAM; Android 16. **Текущая версия:** 0.3.9 (аудит — `AUDIT_v0.3.1.md`, модули — README). **Цель:** стабильная, локальная камера с потенциально более качественной съёмкой по результатам тестов. **Статус:** APK не собирался, на телефоне не проверялся.

Основные правила:
- Работай с имеющимися исходниками, сохраняя все функции. При каждом «Дальше» делай новый реальный этап реализации.
- **НЕ СОБИРАТЬ APK/AAB/EXE и НЕ делать ZIP** до отдельного запроса; если есть SDK, используй только проверку/компиляцию и unit-тесты, которые не создают APK/AAB.
- **Не включать автоматический APK build при push**. Существующий GitHub Actions workflow только ручной.
- Локальная обработка без INTERNET, SDK аналитики, рекламы и root.
- Проверять возможности по Camera2/CameraX, не обещать всех объективов, 50 Мп, 4K, RAW, OEM Night/HDR.
- Серия из 3 JPEG не является Google HDR+ / Night Sight; не вводить пользователя в заблуждение.
- Перед использованием нового AndroidX API добавь его в `tools/api-check/required-apis.txt` и проверь `check-apis.sh` по сигнатурам выбранной версии (вызовы платформы — в `required-framework-apis.txt` и `check-framework-apis.py`); не делай выводов по пересказам release notes (так в аудите 0.3.1 ошибочно решили, что `ExtensionSessionConfig` нет в 1.6).
- Проверка без APK: workflow `verify-sources.yml` (только вручную); офлайн — `tools/offline-check/check.sh` (новые API добавлять в его заглушки).
- Изменения `BurstDenoiser` сравнивать `tools/offline-check/bench.sh` (передай путь к старой версии как аргумент) и заносить результаты в README.
- UI: вёрстка — только `CameraScreen`/`CameraWidgets`; решения UI — чистые функции в `UiModel`. Activity — портретная, ориентация снимков из `OrientationEventListener`.
- Параметры Camera2 (Camera2CameraControl) — только через `ProControls.plan` → `applyRequestOptions()`, одним набором; не вызывать `setCaptureRequestOptions` из других мест.
- Значимые события и ошибки писать в `AppLog.log` (без личных данных); задержки — `log.latency(kind, ms)`.
- После теста на телефоне: начинать с файла диагностики (раздел «Проверка сочетаний») и `DEVICE_TEST_PROTOCOL.md`, а не с предположений о чипсете.
- Новую логику решений писать чистыми функциями (как `SessionPlanner`, `CameraPolicy`) с unit-тестами; `MainActivity` — только UI и оркестрация.
- После каждого этапа: изменённые файлы, выполненные тесты, неподтверждённые части, следующий шаг.
